1. System Overview — Three-Tier Architecture

Reex operates as a three-tier system: a hosted cloud UI, a local CLI bridge running in the developer's terminal, and the developer's own project on disk.

2. Data Flow — From Definition to Generated Code

The complete pipeline when a developer writes or modifies an API definition file. Shows all services involved in the regeneration cycle.

sequenceDiagram
    participant Dev as Developer
    participant Def as definitions/*.ts
    participant Watch as WatcherService
    participant Gen as GeneratorService
    participant Proj as ProjectService
    participant Hook as HookService
    participant Type as TypeService
    participant SSE as SseService
    participant UI as Cloud UI

    Dev->>Def: Saves definition file
    Def->>Watch: chokidar detects change
    Watch->>Watch: Debounce 1000ms
    Watch->>SSE: broadcast project:sync-start
    SSE-->>UI: Shows Syncing spinner

    Watch->>Gen: regenerate(targetDir, changedModules)
    Gen->>Proj: pruneUnusedDefinitions()
    Gen->>Proj: generateManifest(definitionsDir)

    Note over Proj: ts-morph parses each .ts file.
    Note over Proj: getInitializerObject() unwraps
    Note over Proj: as/satisfies/TypeAssertion wrappers.
    Note over Proj: Extracts args, URL, method, auth.

    Proj-->>Gen: Returns manifest JSON

    Gen->>Hook: generateHooks(manifest)
    Note over Hook: Generates useXxxQuery hooks
    Note over Hook: Generates useXxxMutation hooks
    Note over Hook: Creates key factories
    Note over Hook: Handles name collisions

    Gen->>Type: generateTypes(manifest)
    Note over Type: Creates type scaffolds
    Note over Type: Preserves user overrides

    Gen->>Gen: Generate barrel file
    Gen->>Gen: Scaffold templates if missing
    Gen->>Gen: Run Prettier
    Gen->>Gen: Sanitize directory

    Gen->>SSE: broadcast project:updated
    SSE-->>UI: Refreshes manifest and sidebar

4. AST Parsing Pipeline — getInitializerObject()

The centralized utility that all 6 AST processors rely on to safely read API definition files regardless of TypeScript syntax wrappers.

graph TD
    A["variableDecl.getInitializer()"] --> B{initializer exists?}
    B -- No --> RET_UNDEF["return undefined"]
    B -- Yes --> C{SyntaxKind check}
    
    C -- "AsExpression\n(x as Type)" --> UNWRAP["initializer =\ninitializer.getExpression()"]
    C -- "SatisfiesExpression\n(x satisfies Type)" --> UNWRAP
    C -- "TypeAssertionExpression\n(‹Type›x)" --> UNWRAP
    C -- "NonNullExpression\n(x!)" --> UNWRAP
    C -- "ParenthesizedExpression\n((x))" --> UNWRAP
    
    UNWRAP --> C
    
    C -- "ObjectLiteralExpression\n({ ... })" --> RET_OBJ["return ObjectLiteralExpression ✅"]
    C -- "Any other kind" --> RET_UNDEF2["return undefined"]

5. File Watcher Flow

How chokidar detects file changes and triggers smart, debounced regeneration with selective module targeting.

graph TD
    A["chokidar.watch()"] --> B["Monitors:\ndefinitions/*.ts\napi.config.ts"]
    B --> C{Which file changed?}
    
    C -- "api.config.ts" --> D["Debounce 500ms"]
    D --> E["SSE: project:updated\nUI refreshes config only"]
    
    C -- "definitions/*.ts" --> F["SSE: project:sync-start"]
    F --> G["Collect changed files into Set"]
    G --> H["Debounce 1000ms\nCoalesces rapid saves"]
    H --> I["Extract module names\nfrom filenames"]
    I --> J["regenerate(targetDir,\nchangedModules)"]
    J --> K["SSE: project:updated\nFull UI refresh"]

6. Operation Relay Pattern

The UI cannot write files directly. It uses a relay pattern where the Next.js server computes changes and the browser forwards them to the local bridge.

sequenceDiagram
    participant User as User Browser
    participant Next as Next.js API Route
    participant Bridge as Local Bridge
    participant Disk as Filesystem
    participant Watch as Watcher

    User->>Next: POST /api/delete-item
    
    Note over Next: ts-morph parses definition
    Note over Next: Removes function property
    Note over Next: Removes related interfaces
    Note over Next: Removes dangling imports
    Note over Next: Computes file operations

    Next-->>User: { operations: [write, delete] }

    User->>Bridge: POST /api/fs/write
    Bridge->>Disk: fs.writeFileSync()
    Bridge-->>User: success

    User->>Bridge: POST /api/fs/delete
    Bridge->>Disk: fs.unlinkSync()
    Bridge-->>User: success

    Disk->>Watch: chokidar detects change
    Watch->>Watch: GeneratorService.regenerate()
    Watch-->>User: SSE: project:updated

7. Generated Directory Structure

The api-services/ directory created and managed by Reex inside the developer's project. ✏️ User-Authored 🤖 Auto-Generated 📦 Scaffolded Once

my-react-app/ ├── src/ │ └── api-services/ ← Reex-managed directory │ ├── api.config.ts ← 📦 User config (baseURL, auth) │ ├── core.ts ← 📦 HTTP client builder (scaffolded once) │ │ │ ├── definitions/ ← ✏️ USER-AUTHORED (Source of Truth) │ │ ├── users.ts ← export const usersApi = { get_users: ..., post_createUser: ... } │ │ ├── products.ts │ │ └── index.ts ← 🤖 Auto-generated barrel (re-exports all modules) │ │ │ ├── generated/ ← 🤖 AUTO-GENERATED (Do Not Edit) │ │ ├── useUsersQueries.ts ← useGetUsersQuery, usePostCreateUserMutation │ │ ├── useProductsQueries.ts │ │ └── index.ts ← useApiQuery, useApiMutation wrappers + re-exports │ │ │ ├── types/ ← 🔧 SEMI-GENERATED (User can override) │ │ ├── users/ │ │ │ ├── get_users.ts ← export type get_users = unknown; (or user-defined) │ │ │ └── post_createUser.ts │ │ └── products/ │ │ │ ├── hooks/ ← 📦 Utility hooks (useAuthSession, useNotification, useHeaders) │ ├── providers/ ← 📦 React providers (QueryClient, Auth) │ ├── auth-methods/ ← 📦 Auth strategy implementations │ ├── custom/ ← ✏️ Safe zone for user's custom code │ └── .reex/ ← Metadata (port, collection name) │ └── metadata.json
